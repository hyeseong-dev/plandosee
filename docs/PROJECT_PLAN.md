# plandosee · 제품 및 실행 계획

작성일: 2026-09-10 · 버전: 0.1 · 상태: 검토 가능한 기획 초안

## 제품의 중심

**내가 생각한 하루와 실제로 보낸 시간을 나란히 읽고, 다음 계획에서 바꿀 점 한 가지를 남긴다.**

이 문장은 원문에 나타난 계획·실행·돌아보기·개선점 전달을 연결한 AI의 제품 목표 제안이다. 첫 사용자는 과제를 수행하며 자신의 계획과 실제 기록을 입력하는 사용자로 가정한다. 사용자 조사나 선호도 실험을 수행한 결과는 아니다.

단체 공통 과제이므로 필수 기능이 겹치는 것은 자연스럽다. 차별화의 중심은 정보의 배치, 기록하는 순간의 부담, 계획과 실제의 연결, 돌아보기 문장의 쓰임새에 둔다. 장식만 다르고 모든 화면이 같은 통계 카드로 구성되는 결과는 사용자의 의도와 맞지 않는다.

## 제품 경험의 차별화 제안

| 경험 | 화면에서 보이는 모습 | 사용자에게 필요한 이유 | 원문 연결 |
| --- | --- | --- | --- |
| 계획과 실제의 짝 | 같은 할 일에서 ‘예상 30분 / 실제 45분 / 차이 +15분’을 함께 표시 | 기억으로 비교하지 않고 기록으로 차이를 확인 | C17, C23–C27, C32 |
| 기록에 닿는 숫자 | 돌아보기 숫자와 ‘해당 기록 보기’가 하나의 선택 영역 | 어떤 할 일이 집계에 포함됐는지 확인 | C28–C32, C83 |
| 다음으로 가져갈 한 가지 | 돌아보기 하단의 개선점 한 줄, 다음 계획에서 출처와 함께 표시 | 돌아보기가 다음 행동에 이어짐 | C33 |
| 부드러운 기록 흐름 | 목록 안에서 할 일 추가, 상세 패널에서 실제 시간·막힘 기록 | 화면 이동과 문맥 상실을 줄임 | C09–C17, C23–C26 |
| 작은 정원 | 여백, 둥근 잎 실루엣, 약한 민트·살구색, 소량의 새싹 장식 | 사용자가 원한 귀엽고 모던한 인상 | 사용자 디자인 요청 |

여기서 `Cxx`는 원문 `T06-Cxx`의 축약 표기다. 상세 추적표에서는 전체 ID를 사용한다. 위 동작의 구체적 배치는 AI 제안이며, 새싹 장식에 점수·레벨·연속 출석 같은 별도 규칙을 부여하지 않는 방향을 제안한다.

‘만족도 90%’, ‘기록 시간 50% 단축’ 같은 근거 없는 성과 수치는 정하지 않는다. 테마 선호와 사용 편의성은 실제 화면을 본 사용자의 판단으로 남긴다.

## 첫 버전 범위

**포함:** 계획 기간·우선순위·성공 기준·예상 시간과 수정 전 값 보존, 할 일 관리·검색·필터·명시적 정렬, 실행 기록, 돌아보기와 상세 기록 이동, 개선점 전달, 서버 DB·새로고침 복원·전체 내보내기, 공개 안내·입력 안전성·제출 자료.

계획을 새로 만들고 선택하는 기본 흐름과 이력을 확인하는 UI는 위 요구를 사용 가능한 제품으로 연결하기 위한 설계 제안이다. 이력 복원, 계획 삭제, 실행 기록 편집·삭제까지 원문에 명시된 것으로 취급하지 않는다.

**초기 제외 제안:** 회원가입·로그인, 팀 권한·초대, 채팅, 실시간 공동 편집 기능, AI 자동 평가·자동 회고, 달력 외부 연동, 알림·반복 할 일, 포모도로, 테마 상점·보상 경제, 자유로운 드래그 정렬, 전체 데이터 가져오기. 원문 요구를 완료한 뒤 별도 요청이 있을 때 범위를 다시 정한다.

공통 과제라는 사실은 앱에 팀 기능이 필요하다는 뜻이 아니다. 로그인 없는 공개 접근은 원문 조건이다. 공개 편집의 구체적 범위와 데이터 운영 방식은 D-09에서 결정한다.

## 화면과 사용 흐름

메인 이동은 **오늘 / 계획 / 돌아보기**의 세 곳으로 제안한다. 설정 성격의 전체 내보내기와 공개 안내는 눈에 보이는 보조 메뉴로 둔다. 장식적인 별명은 보조 문구에만 쓰고 핵심 이동명은 이해 가능한 한국어로 유지한다.

| 화면 | 첫 화면에서 보는 것 | 주요 행동 | 연결된 원문 |
| --- | --- | --- | --- |
| 오늘 | 공개 안내, 선택된 계획·날짜 범위, 계획과 실제가 짝지어진 할 일, 명시된 검색/필터/정렬 | 할 일 추가·완료·되돌리기, 실행 기록 열기 | C09–C27, C82 |
| 계획 | 계획 목록과 선택, 기간·우선순위·성공 기준·예상 시간, 이전 개선점 | 계획 작성·수정, 이전 버전 확인, 소속 할 일 이동 | C04–C08, C33 |
| 할 일 상세 패널 | 내용·마감일·태그·우선순위·예상 시간, 완료 상태, 실행 기록 목록 | 내용 수정, 실행 시간·막힘 입력, 삭제 | C10–C17, C23–C27 |
| 돌아보기 | 선택된 계획, 범위 설명, 계획 수·완료·지연·막힘, 예상/실제/차이, 개선점 | 집계 상세 보기, 개선점 저장·다음 계획으로 전달 | C28–C33, C83 |
| 자료 내보내기 | 포함되는 자료와 단위, 파일 내보내기 버튼 | 파일 하나 내려받기 | C36 |

‘오늘’ 화면도 현재 선택한 계획을 명확히 표시한다. 오늘 마감만 보는 필터는 선택 사항이며, 이를 켠 상태의 작은 숫자를 계획 전체 돌아보기 숫자로 잘못 표시하지 않는다. 돌아보기 기본 집계에는 할 일 목록의 임시 검색어·필터를 묵시적으로 적용하지 않는 방향을 제안한다.

### 계획에서 실행까지

1. 계획에서 기간·성공 기준·우선순위·예상 시간을 입력한다. 개선점을 가져온 경우 출처를 확인한다.
2. 할 일을 추가하고 필요한 마감일·우선순위·태그·예상 시간을 채운다.
3. 실제 일을 한 뒤 할 일 상세에서 시작·종료와 막힌 이유를 기록한다. 완료 상태 변경과 실행 시간 저장은 별개로 제공한다.

계획의 예상 시간과 소속 할 일 예상 시간 합계는 다른 값일 수 있다. 계획 필드를 자동으로 합계로 덮어쓰지 않는다. 돌아보기 예상 시간은 원문 C32에 따라 대상 할 일 예상 시간 합계이며, 화면에 그 출처를 표시한다.

### 돌아보기에서 다음 계획까지

1. 돌아보기에서 선택된 계획과 집계 범위를 확인한다.
2. 궁금한 숫자를 눌러 해당 할 일·실행 기록과 시간 내역을 확인한다.
3. 사용자가 개선점 한 건을 적고, 새로 만들거나 선택한 다음 계획으로 전달한다는 흐름을 제안한다.

사용자의 판단을 돕는 질문은 ‘예상과 달랐던 점이 있었나요?’처럼 둔다. 시스템이 근거 없이 ‘시간 관리가 부족했어요’라고 평가하거나 개선점을 사용자 대신 확정하지 않는다.

## 데이터와 저장 구조 제안

아래는 논리 모델이며 실제 DB 스키마나 기술 스택의 확정이 아니다. 전체 자료는 실제 서버 DB에 저장해야 한다는 C34는 별도의 원문 의무다.

| 개념 | 핵심 값·관계 | 보존해야 할 의미 |
| --- | --- | --- |
| 계획 | ID, 기간, 우선순위, 성공 기준, 예상 시간 | 현재 계획과 수정 전 값을 식별 가능하게 보존 |
| 계획 버전 | 계획 ID, 버전 ID, 당시 필드 값, 생성 시각 | 이후 수정·실행 저장이 이전 값을 바꾸지 않음 |
| 할 일 | ID, 계획 ID, 내용, 상태, 마감일, 우선순위, 태그, 예상 시간 | 집계의 기본 단위. 삭제 처리 정책은 D-04 |
| 실행 기록 | ID, 할 일 ID, 시작·종료, 실제 시간, 막힌 이유 | 동일 할 일에 여러 건 가능하다는 설계 제안; 계획과 분리 |
| 완료 사건 | ID, 할 일 ID, 완료 주기, 완료 시각 | 중복 요청의 처리 증거. 현재 완료 수의 직접 합산 원천은 아님 |
| 돌아보기 | ID, 계획 ID, 사용자가 적은 돌아보기·개선점 | 메모는 저장하고 기본 집계는 현재 자료에서 계산하는 제안 |
| 개선점 전달 | 돌아보기 ID, 개선점, 대상 계획 ID | 다음 계획에서 원래 돌아보기로 추적 가능하게 연결 |

브라우저 → 서버 API → 실제 데이터베이스의 저장 경로를 제안한다. DB 연결 비밀은 서버에만 두고, 화면에는 저장 여부와 복구 가능한 오류를 표시한다. 브라우저 임시 상태는 입력 편의를 위한 것이며 서버 저장 완료를 대신하지 않는다.

완료 중복 방지는 UI 버튼의 일시 비활성화와 서버의 원자적 상태 변경을 함께 검토한다. DB 트랜잭션·고유 제약은 구현 후보다. 버튼 두 번 누르기만 막고 다른 탭의 요청에서 기록이 중복되는 반례도 검사 계획에 포함한다. 구체적 구현 방식이 원문 의무인 것처럼 고정하지 않는다.

### 돌아보기 계산의 기준

아래 `S`의 범위는 D-03의 AI 제안이다. C28과 C29의 미삭제 할 일 범위는 원문에 명시되어 있으며, 나머지 지표에도 이를 일관되게 적용하는 부분을 제안한다.

| 항목 | 계산 | 화면 설명 |
| --- | --- | --- |
| 대상 `S` | 선택한 계획 소속 중 삭제되지 않은 할 일 | 계획 기간 밖의 실행 포함 여부는 D-03 |
| 계획 수 | `S`의 할 일 수 | ‘계획 수’ 옆에 ‘등록한 할 일’ 보조 설명 |
| 완료 수 | `S` 중 현재 완료 상태 수 | 완료 사건 총수가 아님 |
| 지연 수 | `S` 중 미완료이면서 마감일이 서울 기준 오늘보다 이전인 수 | 오늘 마감·마감일 없음·완료는 제외 |
| 막힘 수 | `S` 중 막힌 이유가 하나라도 기록된 할 일 수 | 같은 할 일에 이유가 여러 건이어도 1 |
| 예상 시간 | `S`의 할 일 예상 시간 합계 | 계획 자체 예상 시간과 구분 |
| 실제 시간 | `S`의 실행 기록 실제 시간 합계 | 완료 여부와 무관하게 기록을 합산 |
| 차이 | 실제 시간 − 예상 시간 | 양수는 더 쓴 시간, 음수는 덜 쓴 시간; 좋고 나쁨의 점수가 아님 |

빈 집계는 0을 표시한다. 막힘·지연·완료는 서로 배타적인 전체 분류가 아니다. 예를 들어 완료한 할 일에도 막힌 기록이 있으면 완료와 막힘에 각각 포함될 수 있으므로, 세 숫자를 합쳐 전체 할 일 수로 쓰지 않는다.

숫자 상세에서는 계획 수는 모든 대상 할 일, 완료·지연·막힘은 해당 조건의 할 일, 예상 시간은 할 일별 예상, 실제 시간은 실행별 내역, 차이는 두 내역의 대조를 보여주는 방향을 제안한다. 합계가 변하면 상세와 요약을 같은 시점의 자료로 갱신한다.

각 D-ID는 문서 관리용이다. 원문 `T06-Cxx`를 추가하거나 변경하지 않는다. 아래 제안은 구현 초안을 위한 기준이며 아직 사용자가 선택했다고 기록하지 않는다.

결정이 달라지면 이 표의 상태·날짜·이유를 기록하고, 영향을 받는 요구사항 설명·디자인·검증 시나리오를 함께 수정한다. 원문 조건의 변경은 별도로 사용자 근거를 남긴다.

## 구현 단계와 완료 증거

소요 기간·마감일·담당 인원은 아직 미확정이다. 아래 순서는 의존 관계에 따른 제안이며 날짜나 성과를 약속한 일정이 아니다.

| 단계 | 산출물 | 다음 단계로 갈 근거 |
| --- | --- | --- |
| 1. 기획과 대표 화면 | 현재 문서, 정책 결정 기록, 실제 한글을 넣은 오늘·돌아보기 시안 | 원문 추적 확인, 테마 방향·주요 기록 정책 확인 |
| 2. 기반과 저장 | 서버 DB, 최소 저장 API, 비밀 분리, 왕복 복원 | ID·날짜·값·단위가 새로고침 뒤 일치 |
| 3. 계획과 할 일 | 계획 보존, CRUD, 검색·필터·정렬, 기본 모바일 UI | 관련 시나리오와 공개 안내 확인 |
| 4. 실행과 완료 | 실행 저장·계획 분리, 완료·되돌리기, 중복 완료 처리 | 연속 클릭·동시 요청의 DB 기록과 현재 완료 수 확인 |
| 5. 돌아보기와 다음 계획 | 정확한 집계, 숫자 상세 이동, 개선점 전달 | 고정 시험 자료와 계산값·상세 집합 일치 |
| 6. 디자인·제출 완성 | 폰트·상태·키보드·모바일 점검, 내보내기, 실제 자료, 확인 안내·AI 사용 기록 | 44개 조건의 실제 증거, 인증 없는 결과물·소스 URL 확인 |

장식이나 부가 기능을 위해 필수 단계의 일부를 생략하지 않는다. 처음부터 핵심 화면에서 디자인 방향을 반영하고, 마지막 단계에서만 외형을 덧붙이는 흐름을 피한다는 설계 제안이다.

## 내보내기와 공개 제출

내보내기 파일에는 계획, 계획 이력, 할 일, 실행 기록, 돌아보기, 보존한 완료 사건과 개선점 연결을 담는 방향을 제안한다. ID와 관계, 날짜·시간대, 숫자와 단위를 보존한다. 서버 비밀·내부 연결 문자열·사용하지 않는 환경설정은 포함하지 않는다.

첫 화면에는 아래 원문 문장을 그대로 읽을 수 있게 표시한다. 테마 장식·닫힌 도움말·첫 방문 모달 안에만 두지 않는다.

## 검증과 남은 일

검사 설계는 [VERIFICATION.md](VERIFICATION.md)에 있다. 합성 시험 데이터의 통과와 사용자의 실제 기록 요건 충족은 별개다. 계획 수·완료 수·막힘 수·시간 합계의 반례를 실제 DB와 UI에서 확인한 뒤 결과와 증거를 기록한다.

현재 수행한 일은 문서 작성과 원문·추적 관계의 검토다. 앱 실행, DB 검증, 시크릿 창의 배포 검증, 사용자 사용성 평가, 형식 검증은 수행하지 않았다.

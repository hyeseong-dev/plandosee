# PlanDoSee 검증 계획

작성 기준: `constitution.txt`의 인수 조건 44개, 사용자가 요청한 모던하고 귀여우며 둥근 UI, 명확하고 낡아 보이지 않는 글씨체.

문서 상태: **검사 설계 완료 / 제품 검사 전 항목 미실행**. 아래 통과 기준과 예시는 예상 결과이며 실제 실행 결과나 구현 완료의 증거가 아니다. 구현 방식과 기술 스택은 이 문서에서 지정하지 않는다.

## 1. 판정과 증거를 남기는 방법

- 원문 조건은 `T06-Cxx`로 추적한다. 제품의 합격 근거는 해당 조건과 실제 검사 증거를 함께 기록한다.
- 실행할 때 각 시나리오에 실행일, 검사한 배포 버전, 실제 결과, 상태(통과·실패·보류), 증거 위치를 붙인다. 현재 상태는 모두 **미실행**이다.
- 화면 캡처만으로 서버 저장, 중복 방지 또는 비밀키 부재를 판정하지 않는다. 필요한 경우 화면과 서버 DB 조회, 네트워크 결과, 소스·배포 산출물 확인을 함께 사용한다. 증거에는 비밀키를 담지 않는다.
- 합성 자료로 기능을 검사한 결과와 사용자가 실제 자료를 넣어 제출 요건을 충족한 결과를 분리한다. 아래 테스트 예시는 실제 사용자 기록을 대신하지 않는다.

## 2. 검사에 필요한 제안 정책

다음은 검사 결과를 일관되게 판단하기 위한 **AI 제안**이다. 원문에 없는 세부 규칙이므로 확정 요구사항으로 표시하지 않는다. 정책의 관리 기준은 [프로젝트 계획의 D-01–D-13](PROJECT_PLAN.md#정책-제안과-미결정-사항)이다. 이 문서의 P-ID는 검사를 위한 별칭이며, 프로젝트 계획에서 정책을 변경하면 관련 기대값도 함께 바꾼다.

| 정책 | 제안 내용 | 영향 |
| --- | --- | --- |
| P01 돌아보기 범위 | 선택한 계획의 비삭제 할 일 전체와 그 할 일에 속한 실행 기록 전체를 집계한다. 계획 기간 밖의 실행 기록도 포함한다. | V06–V10 |
| P02 날짜 | 마감일은 시각 없는 날짜로 저장하고, 오늘은 `Asia/Seoul` 기준으로 계산한다. 같은 검사에서 화면과 서버의 기준 시점을 고정한다. | V07, V12 |
| P03 시간 | 시간의 저장·계산 기준은 정수 초, 화면은 분을 중심으로 초까지 손실 없이 표시한다. 실제 시간은 종료 시각 − 시작 시각이다. 원래 값으로 합산한 후 표시한다. 입력하지 않은 할 일 예상 시간은 집계에서 0으로 계산하고 개별 화면에는 미입력으로 표시한다. | V05, V09, V12 |
| P04 완료 주기 | 완료 → 진행 중 → 완료는 서로 다른 완료 주기다. 완료 이벤트는 주기별로 보존하되, 돌아보기 완료 수는 현재 상태로 계산한다. 같은 주기의 연속 완료 요청은 이벤트 한 건이다. | V04, V06 |
| P05 삭제·보존 | 소프트 삭제를 사용하고 삭제된 할 일·연관 기록을 보존한다. 돌아보기에서는 제외하고 전체 내보내기에는 삭제 표시와 함께 포함한다. | V02, V06, V13 |
| P06 개선점 전달 | 사용자가 대상이 될 다음 계획을 선택한다. 전달한 개선점은 출처 돌아보기와 연결하여 두 화면에서 확인한다. | V11 |

계획 수정 전 내용을 보존해야 한다는 조건은 원문 요구다. 보존 중인 수정 전 계획은 전체 자료 내보내기에서도 삭제 방식과 무관하게 확인한다. 소프트 삭제, 이력 복원 UI, 완료 이벤트의 주기별 보존, 대상 계획 선택 방식은 원문 자체가 지정한 구현 방식이 아니다.

정책 연결: P01 → D-03, P02 → D-02, P03 → D-02·D-06·D-13, P04 → D-05, P05 → D-04·D-12, P06 → D-07. 검색·정렬은 D-08을 따른다. 원문 상태 전환·집계 의무는 이 제안 정책의 채택 여부와 무관하게 검사한다.

## 3. 합성 테스트 자료와 기준값

**기능 검사 전용 자료다. `T06-C78`–`T06-C81`의 실제 자료로 제출하지 않는다.**

기준 시각은 `2026-09-10T00:00:00+09:00`이며 UTC로는 `2026-09-09T15:00:00Z`다. 계획 P의 기간은 2026-09-07–2026-09-13, 계획 자체 예상 시간은 180분으로 둔다. 할 일 예상 시간 합계와 계획 예상 시간을 다르게 두어 집계 대상을 구분한다.

| 할 일 | 현재 상태 | 마감일 | 예상 | 실제 실행 기록 | 막힌 이유가 있는 기록 | 돌아보기 포함 |
| --- | --- | --- | ---: | --- | ---: | --- |
| A 자료 읽기 | 완료 | 2026-09-08 | 30분 | 15분 + 25분 | 2개 | 포함 |
| B 구조 스케치 | 진행 중 | 2026-09-09 | 20분 | 10분 | 1개 | 포함 |
| C 문장 정리 | 진행 중 | 2026-09-10 | 15분 | 5분 | 0개 | 포함 |
| D 폴더 준비 | 완료 | 2026-09-11 | 0분 | 없음 | 0개 | 포함 |
| E 화면 구상 | 진행 중 | 없음 | 25분 | 없음 | 0개 | 포함 |
| F 버린 초안 | 삭제 | 2026-09-08 | 60분 | 60분 | 1개 | 제외: P05 |

A의 두 실행 기록은 2026-09-09 서울 시각 09:00–09:15와 10:00–10:25, B는 11:00–11:10, C는 12:00–12:05로 둔다. A의 이유는 각각 “자료 접근 지연”, “용어 확인”, B의 이유는 “구조 결정 필요”다. 다른 계획 Q에는 완료된 할 일 한 개와 100분 실행 기록을 넣어 선택한 계획 밖 자료의 유입을 검사한다.

| 돌아보기 항목 | 기대값 | 산식 또는 포함 대상 |
| --- | ---: | --- |
| 계획 수 | 5 | A, B, C, D, E |
| 완료 수 | 2 | A, D |
| 지연 수 | 1 | B. A는 완료, C는 오늘 마감이므로 제외 |
| 막힘 수 | 2 | A, B. 막힌 이유가 있는 기록 3개를 할 일 2개로 계산 |
| 예상 시간 | 90분 / 5,400초 | 30 + 20 + 15 + 0 + 25 |
| 실제 시간 | 55분 / 3,300초 | 15 + 25 + 10 + 5 |
| 차이 | −35분 / −2,100초 | 실제 − 예상 |

B는 지연과 막힘에 동시에 속한다. 분류 간 중복은 가능하므로 완료·지연·막힘 수를 더해 계획 수를 만들지 않는다. **고정 자료를 사용하는 각 시나리오 시작 전에는 별도의 테스트 공간에서 위 기준 자료와 시각으로 복원하거나 새 자료 세트를 준비한다.** 직전 검사에서 변경한 상태를 그대로 넘기지 않는다. 예를 들어 V06에서 A를 진행 중으로 되돌린 뒤에는 A를 기준 완료 상태로 복원한 자료로 V07을 시작해야 0→1이라는 지연 기대값이 성립한다. 실제 사용자 자료를 초기화 대상으로 사용하지 않는다.

## 4. 짧은 확인 방법: 18개 시나리오

각 항목은 어디로 가는지, 세 단계 이내 행동, 통과 모습, 실패 모습을 나누어 제공한다. **V01–V18의 현재 실행 상태는 모두 미실행**이다.

### V01 계획값과 수정 전 계획 보존

대상: `T06-C04`, `T06-C05`, `T06-C06`, `T06-C07`, `T06-C08`.

- ① 어디: 계획 작성·상세 화면과 계획 수정 이력을 확인할 수 있는 위치.
- ② 행동: 1) 기간·우선순위·성공 기준·예상 시간을 정해 계획을 저장한다. 2) 네 값을 다른 값으로 바꾸어 저장한다. 3) 현재 계획과 수정 전 기록을 확인한다.
- ③ 통과: 현재 계획에는 변경값이 있고, 수정 전의 네 값과 해당 계획 내용도 온전히 남아 있다. 두 상태의 출처를 구분할 수 있다.
- ④ 실패: 입력값 일부가 저장되지 않거나, 수정 전 내용이 변경값으로 덮어써지거나, 이전 상태가 없어졌다.

증거: 변경 전·후 값, 이력 식별자와 보존된 데이터. 이력을 되돌리는 기능까지 원문 합격 조건으로 추가하지 않는다.

### V02 할 일 만들기·수정·삭제와 속성 저장

대상: `T06-C09`, `T06-C10`, `T06-C13`, `T06-C14`, `T06-C15`, `T06-C16`, `T06-C17`.

- ① 어디: 선택한 계획의 할 일 목록과 할 일 편집 화면.
- ② 행동: 1) 내용·마감일·우선순위·태그·예상 시간이 있는 할 일을 만든다. 2) 내용을 수정한 뒤 저장된 속성을 다시 확인한다. 3) 해당 할 일을 삭제한다.
- ③ 통과: 작성값과 수정값이 정확하고 계획 소속을 유지한다. 삭제 후 일반 목록과 돌아보기 대상에서 빠진다. P05를 채택했다면 삭제 표시가 있는 원본과 연관 기록은 보존된다.
- ④ 실패: 속성이 유실되거나 다른 계획으로 옮겨지거나, 삭제한 할 일이 일반 목록 또는 계획 수에 계속 포함된다.

### V03 검색·필터·표시한 정렬 기준

대상: `T06-C18`, `T06-C19`, `T06-C20`.

- ① 어디: 할 일 목록의 검색·필터·정렬 영역.
- ② 행동: 1) 포함할 것과 제외할 것이 명확한 제목·태그·상태 자료를 준비한다. 2) 검색과 필터를 적용하고 해제한다. 3) 화면에 설명된 정렬을 선택한 뒤 동일 조건에서 목록을 다시 연다.
- ③ 통과: 검색·필터 결과의 포함·제외가 선택 조건과 맞고, 정렬이 화면의 설명과 일치한다. 동률 처리도 설명된 규칙에 따라 같은 순서를 유지한다.
- ④ 실패: 조건에 맞지 않는 항목이 나오거나 맞는 항목이 누락된다. 정렬 설명이 없거나 실제 순서가 설명과 다르거나 동률 항목이 임의로 바뀐다.

동률 규칙과 검색 범위는 제품에서 명시할 제안 정책이다. D-08의 기본 정렬 제안은 미완료 먼저 → 마감일 빠른순(없음 뒤) → 높은 우선순위 → 생성 시각 → ID다. 이 순서 자체는 원문 요구가 아니며, 선택한 정렬과 화면 설명의 일치가 원문 요구다.

### V04 연속 완료의 중복 방지와 되돌리기

대상: `T06-C11`, `T06-C12`, `T06-C21`, `T06-C22`.

- ① 어디: 테스트 자료 E의 완료 버튼, 완료 기록, 계획 P의 돌아보기.
- ② 행동: 1) E가 진행 중이고 완료 수가 2임을 기록한다. 2) E의 완료 버튼을 연달아 두 번 누른다. 3) 서버 처리 후 E의 상태·완료 기록·돌아보기를 확인한다.
- ③ 통과: E는 완료이고 해당 연속 요청에 대한 완료 기록은 정확히 한 건이다. 돌아보기 완료 수는 2에서 3으로 정확히 1만 늘어난다. 추가 반례 검사로 두 요청이 동시에 서버에 도달하는 상황을 구성하고 같은 결과인지 확인한다.
- ④ 실패: 완료 이벤트가 두 건이거나 완료 수가 4가 된다. 버튼이 잠깐 비활성화되는 모습만 확인하고 서버 중복 여부를 판정하는 것도 증거 부족이다.

되돌리기·재완료 확인 — 상태·현재 집계는 원문 검사, 주기별 이력 보존은 P04 채택 때만 검사:

- ① 어디: 같은 E의 상태 변경과 완료 이력.
- ② 행동: 1) E를 다시 진행 중으로 바꾼다. 2) 돌아보기 완료 수를 확인한다. 3) E를 다시 완료하고 상태·이력을 확인한다.
- ③ 통과: 되돌린 뒤 현재 완료 수는 2, 재완료 뒤 3이다. P04에서는 E의 두 완료 주기 이벤트가 보존되지만 집계는 현재 완료된 E 한 개만 센다.
- ④ 실패: 진행 중으로 되돌릴 수 없거나 집계가 3에 남는다. 재완료 후 집계가 누적 이벤트 수 때문에 4가 된다. 이벤트 보존 방식은 원문과 구분해 P04 채택 여부로 판정한다.

### V05 실행 기록과 원래 계획의 분리

대상: `T06-C23`, `T06-C24`, `T06-C25`, `T06-C26`, `T06-C27`.

- ① 어디: 계획 상세와 해당 할 일의 실행 기록 작성·상세 화면.
- ② 행동: 1) 계획의 현재 값과 수정 전 이력을 기록한다. 2) 시작·종료 시각 및 막힌 이유가 있는 실행 기록을 저장한다. 3) 실행 기록과 계획값을 다시 확인한다.
- ③ 통과: 시작·종료·실제 시간·막힌 이유가 저장되고, 계획의 원래 예상 시간·기간·성공 기준·우선순위와 기존 이력은 그대로다. P03 채택 시 09:00–09:15 기록의 실제 시간은 900초이며 화면에 15분으로 표시된다.
- ④ 실패: 실제 시간이 예상 시간을 바꾸거나, 계획 기간이 실행 시각으로 덮어써지거나, 실행 시각·단위·이유가 유실된다.

### V06 계획 수와 현재 완료 수의 집합

대상: `T06-C28`, `T06-C29`.

- ① 어디: 계획 P의 돌아보기와 그 대상 할 일 목록.
- ② 행동: 1) 기준 테스트 자료를 준비한다. 2) 돌아보기의 계획 수·완료 수와 각각의 항목을 확인한다. 3) 완료된 A를 진행 중으로 바꾸어 다시 확인한다.

차이와 0의 상세 표현 방식은 P01에 맞춘 AI 제안이다. 집계 숫자에서 근거 기록으로 갈 수 있어야 한다는 점이 원문 요구다.

저장 실패·응답 지연 시 거짓 성공을 보여 주지 않는지도 보조 검사한다. 돌아보기의 저장 구조는 구현 명세에서 결정하되, 원문의 DB 저장 조건을 충족하는 증거를 남긴다.

대상: `T06-C59`, `T06-C60`.

- ① 어디: 최종 결과물의 짧은 확인 안내와 제출문.
- ② 행동: 1) 안내에서 어디·행동·통과·실패 네 항목을 찾는다. 2) 행동이 세 단계 이내이고 실제 화면으로 수행되는지 확인한다. 3) 제출문의 AI 수행·사용자 판단·AI 제안 미채택 내역을 확인한다.
- ③ 통과: 확인 방법의 네 항목이 각각 구분되어 있고 최종 화면에 맞는다. 제출문은 ① AI에게 맡긴 일, ② 내가 직접 판단한 일, ③ AI 제안을 따르지 않은 일(없다면 왜 없었는지)을 각각 구분하며 실제 수행 사실과 일치한다.
- ④ 실패: 통과와 실패가 섞여 있거나 행동이 네 단계 이상이거나, 안내가 구현 전 화면을 가리키거나, 사용자가 하지 않은 판단·거절을 AI가 만들어 기재한다.

현재 문서는 확인 안내의 초안이다. 최종 안내에는 구현된 화면명·경로를 반영해야 한다. 사용자 판단과 미채택 제안 내역은 사용자에게서 받은 실제 내용으로 완성하고, 아직 확인하지 못한 것은 “확인 필요”로 둔다.

## 5. 디자인 품질 확인

아래는 원문 44개 조건 외에 사용자가 직접 요청한 디자인 방향을 확인하는 보조 검사다. 제품 이미지와 실제 UI를 보고 판정하며, **현재 모두 미실행**이다.

| 항목 | 확인할 모습 | 실패 신호 |
| --- | --- | --- |
| 모던하고 귀여운 인상 | 가벼운 여백, 부드러운 형태, 절제된 색과 친근한 문구가 한 방향으로 이어진다. | 평범한 업무 대시보드에 장식만 붙이거나, 화면마다 서로 다른 톤이다. |
| 둥근 UI/UX | 카드·버튼·입력·레이어의 둥근 형태와 간격이 일관된다. 사용 흐름이 짧고 다음 행동이 보인다. | 각진 구획이 빽빽하거나, 둥근 장식 때문에 클릭 영역과 정보 구조가 불명확하다. |

| 상태 전달 | 완료·진행·지연·막힘은 글자·아이콘·형태 등으로 구분하고 여러 상태가 겹칠 때도 의미가 유지된다. | 색만 보거나 애니메이션이 실행되어야 상태를 알 수 있다. |
| 입력과 안내 | 오류가 해당 필드 가까이 설명되고 키보드 포커스가 보인다. 첫 화면 공개 안내는 장식에 묻히지 않는다. | 오류 위치를 못 찾거나, 귀여운 말투 때문에 실패 이유가 불명확하거나, 안내를 닫아야만 내용을 알 수 있다. |
| 움직임 | 전환은 짧고 필요한 피드백을 돕는다. 움직임 감소 설정에서도 모든 기능과 상태를 이해할 수 있다. | 반복 움직임이 수치를 읽는 것을 방해하거나, 모션이 끝날 때까지 핵심 기능을 쓸 수 없다. |
